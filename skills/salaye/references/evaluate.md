# Evaluate together

Use this mode when the user wants to assess an idea, plan, decision, document, or code candidate against explicit criteria while staying in conversation.

State the evaluation question, criteria, blocking conditions, evidence standard, current focus identity, and expected result. Do not invent universal criteria or a specialist verdict vocabulary.

Use the owning specialist when one exists:

- `qp-code-review` owns defect and broad code-review verdicts;
- `simplify` owns a bounded maintainability-only review;
- `atona` owns architecture or migration plan readiness and delivery state; and
- `arojinle` owns choosing and confirming material branches for an idea, plan, or decision.

When no specialist owns the assessment, evaluate each criterion as `SUPPORTED`, `PARTIAL`, `UNSUPPORTED`, or `UNPROVED`. Give evidence, counterevidence, assumptions, consequence, and the smallest next proof. Do not convert this assessment into approval or a confirmed decision.

Use `ro-wo` when the needed result is only a brief premise check before agreement or disagreement. Ṣàlàyé retains the wider conversational evaluation and user steering.

Steering can change inspection priority but cannot silently drop required coverage. Distinguish provisional concerns, challenged findings, open decisions, and final specialist results. Apply the core pause rule when a missing user constraint, intended meaning, or likely misdirection controls the criteria or next check.

If the user wants an exposed material choice settled, hand the focus, evidence, gaps, and decision scope to `arojinle`. If the user wants implementation or maintained plan delivery, hand off to the applicable owner.

Return the owning specialist's exact-current result without strengthening it, or return the criteria assessment with its evidence, gaps, limitations, and next proof.
