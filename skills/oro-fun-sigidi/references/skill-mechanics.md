# Skill mechanics

Read only when the agent-facing artifact is a skill.

A skill is a packaging and invocation choice around a useful behavioural contract. Do not start from taxonomy. Start from the result a user or another skill needs.

## Public identity is a human decision

A new public skill identity is consequential because it adds routing/context surface and a concept users must understand. Do not create one merely because guidance can be written.

A separate skill should have:

- an independently useful result or steering contract;
- a realistic trigger that should select it directly;
- nearest exclusions that keep adjacent owners distinct; and
- a reason the behaviour cannot live more coherently in an existing owner or instruction surface.

If the user explicitly asked for a new skill, drafting the candidate is authorized; still surface the proposed identity, trigger, and ownership boundary rather than presenting them as self-evident facts. Promotion, removal, folding, or a material routing reassignment remains a separate human decision unless explicitly requested.

## Invocation is part of the design

Choose whether the model must be able to reach the skill autonomously. Model invocation spends always-loaded routing context but enables the agent and other skills to find it. Human-only invocation avoids that context cost but requires the person to remember and call it.

Use the host/package's current invocation controls rather than copying volatile host syntax here. Keep model-invoked descriptions discriminative enough to fire on real trigger branches and reject adjacent ones. Human-only descriptions can optimize browsing instead of autonomous routing.

A compatibility alias should not compete with its replacement. Narrow its description to legacy/explicit-name use and keep the real method at one owner.

## Description is a pointer

The description decides whether the skill becomes reachable. It should state the owned result and distinct trigger branches, plus the nearest meaningful exclusions. Do not summarize the full procedure.

If two skills attract the same realistic request, resolve the ownership/result distinction before adding synonyms to either description.

## Entrypoint and references

Keep in `SKILL.md` only what every invocation needs: focal result, recurring non-obvious decisions, authority/evidence boundaries, completion semantics, and reliable pointers to conditional depth.

Use references when a meaningful branch can be selected independently. Do not split by file length alone. A short root that always forces many references can be worse than a cohesive root.

Keep workflow position out of reusable skill instructions. The workflow/assignment layer may constrain the invocation; the skill should remain independently correct.

## Review a skill portfolio when asked

For an explicitly requested portfolio review, compare public identities, owned results, routing collisions, compatibility aliases, cumulative always-loaded context, and representative end-to-end task paths. Structural counts and lexical overlap are leads, not quality or redundancy verdicts.

Keep the review read-only unless edits are separately authorized. Distinguish a bad instruction from missing/ignored context, unavailable tooling, or model variance before recommending more prose.

## Support lifecycle decisions without taking them over

When the user is deciding whether to promote, narrow, fold, replace, or remove a skill, use real-use evidence where available: eligible opportunities, correct and incorrect selections, missed triggers, observed incremental value/cost, boundary failures, counterevidence, and coverage limits.

Do not infer usage or value from repository shape, raw invocation count, or one successful example. A proved structural defect can justify recommending a change; missing historical evidence remains a gap. Present the evidence and recommendation, but do not enact a public identity or routing change unless that change is explicitly authorized.

## Routers

A router earns its place by encoding useful topology or selection distinctions that individual descriptions do not. Do not gut route shapes merely because the installed inventory is discoverable. Dynamic inventory and route topology solve different problems.

When simplifying a router, show that common paths, adjacent-owner boundaries, skip conditions, and long-tail discovery remain intact. Description matching alone is not an equivalent replacement for semantic routing knowledge.

## Acceptance

Validate the actual changed boundary: selection when routing changed, loading when disclosure changed, authority when action semantics changed, and behaviour when instructions changed materially. Package syntax checks prove package structure only.
