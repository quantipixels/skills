# Alága

Own the requested engineering result using inspected implementation, real consumers and executed evidence. Distinguish known, inferred and unverified. Reuse settled scope and authority.

Enter the requested mode directly:

- issue intake — validate/classify a report through [issue intake](references/issue-intake.md);
- diagnosis — establish the smallest supported causal mechanism through [diagnosis](references/diagnosis.md);
- incident recovery — mitigate/verify an active disruption through [incident recovery](references/incident-recovery.md);
- delivery — implement and verify an accepted coding outcome below.

The first three stop at their requested result and do not authorize delivery. For a supplied repair, use the [existing repair comparison](references/diagnosis-probes.md#existing-repair-comparison) and stop at the requested evidence unless correction is authorized. Use `irinse` when source navigation, tool-evidence semantics or readiness materially affects any mode.

## Deliver an accepted coding change

Within an `atona` initiative, reuse its assignment and return candidate, proof and blockers; `atona` owns progression. Direct requests need no initiative plan.

Trace behavior from entry points through its canonical owner, shared mechanisms, consumers and proof. Search by domain behavior, reuse applicable decisions and establish the actual gap. Apply DRY to shared knowledge and YAGNI to custom state: extend the owner when semantics fit and verify native guarantees before inventing coordination. Make the smallest idiomatic causal fix, preserve unrelated work and surface consequential scope expansion. Record a deliberate limit's ceiling/revisit condition near its owner; preserve real calibration.

When test-first delivery is explicitly requested, choose one stable behavioral seam and independent expected outcome, observe the intended red for the correct reason, implement minimum green, then refactor while preserving affected proof. Reuse an accepted seam without renewed approval. Do not impose this loop on ordinary delivery or substitute it for persistence, integration or user-journey evidence.

For domain values/types/states, follow the authoritative project's naming, representation and lifecycle. Trace enum/status transitions, persisted/wire values, defaults, unknown handling and consumer mappings; distinguish identifiers from labels. Resolve conflicting patterns at their owner rather than copying one.

For changes spanning consumers, persistence, framework-managed behavior, authorization or external effects, read [integration obligations](references/integration-obligations.md) and reconcile them against the final candidate. Route unresolved causal structure to diagnosis and consequential technical structure to `architect`. Existing implementation is evidence, not a requirement to keep extending it.

For an accepted test-suite change, read [test-suite improvement](references/test-suite-improvement.md). For useful input-domain invariants read [property-based testing](references/property-based-testing.md); for scaling arithmetic [units and scaling](references/units-and-scaling.md); for persistence/concurrency/recovery [stateful proof](references/stateful-proof.md). Use project verification specialists for real assembled effects. Tool metrics and generated tests do not replace boundary proof.

Verify the changed contract with evidence capable of detecting a plausible failure. Prefer affected checks or a focused probe; add a test for a material uncovered regression. Confirm checks actually executed against the candidate: zero selection, skips, stale results and successful submission are not passing proof. Attribute pre-existing failures, preserve acceptance, exercise required browser behavior, inspect the final diff and rerun only affected checks.

For dependency resolution, generated output or incremental builds, verify effective inputs and invalidation; a warm pass can hide stale output. Use `irinse` for non-obvious evidence while retaining acceptance here. Use `atunwo` when independent judgment is requested or materially useful, resolve warranted findings and refresh only affected proof.

Finish when behavior and necessary documentation are delivered and verified, or name the exact blocking gap. Report change, decisive verification and limits. Publication belongs to `wo-pr` under existing authority.

An explicit scope-only request returns outcome, boundaries, current evidence/gaps and proposed verification without implementation; distinguish performed from proposed checks.
