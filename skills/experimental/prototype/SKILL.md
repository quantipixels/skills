# Prototype

Build a throwaway decision instrument for one question that discussion, static prose, or a cheaper sketch cannot settle.

> Do not fake the dimension being tested.

A behavior question needs functioning behavior. A visual-reading question needs sufficient visual fidelity. A CLI or API ergonomics question needs a runnable interaction. The prototype exists to produce decision evidence, not to become the product.

## 1. Pin the decision question

State the one material question, why cheaper evidence is insufficient, who must experience the result, the dimension being tested, accepted fidelity, exclusions, disposal boundary, available environment, and any mutation or external-effect authority.

Do not start when the user is actually asking what to build, requesting production implementation, or asking for ordinary visual polish. Use `arojinle` for unresolved consequential choices that do not yet require an artifact and `alaga` for the accepted production result.

When the question depends on subjective experience, require an attending human. An unattended run cannot invent how the interaction feels or what the user prefers.

## 2. Build the minimum truthful artifact

Choose the smallest medium and fidelity that can answer the question. Reuse the project's existing runtime, components, tokens, fixtures, or local server when that improves truth without turning the prototype into production work.

Use an OS temporary directory or isolated disposable workspace by default. Do not modify the production candidate unless the user separately authorizes a bounded prototype location. Avoid real customer data, production credentials, irreversible effects, external messages, or payments. Label simulated behavior clearly, but do not simulate the dimension whose behavior is being decided.

Do not add a bundled preview server merely for this workflow. Use the existing application server, a host-native preview, or a standard available local server.

## 3. Let the user experience and decide

Give the user the runnable path and a concise observation prompt tied to the question. Record what they actually observed, not what the artifact author expected. Revise only when the next version can still answer the same pinned question; a new material question requires a new prototype boundary.

Finish with exactly one result:

- `DECIDED` — the user selected or confirmed an answer from direct experience;
- `INCONCLUSIVE` — the prototype ran but did not discriminate between alternatives;
- `BLOCKED` — a named environment, capability, authority, or human-attendance gap prevented the test; or
- `ABANDONED` — the user ended the experiment without a decision.

Return the question, artifact path, fidelity and simulations, observations, decision or unresolved alternatives, limitations, and next owner. The prototype is evidence. It cannot set the production plan or acceptance state by itself.

## 4. Retain only decision evidence

Temporary work may be deleted after the result is captured. Persist through `akosile` only when the user or caller needs a durable decision-prototype result. A durable HTML prototype may itself be the runnable artifact. Use `html-artifact` only when a separate human report about supplied prototype evidence is useful.

Under an active `arojinle` interview or `atona` plan, return Prototype's exact-current result; the caller owns the resulting decision or plan update.
