# Stack detection

Establish only stack facts that can materially change the Code Craft Brief. Prefer the repository and its own tools; Akọ̀wé Code does not own a universal build-system parser or permanent command catalogue.

## Evidence order

1. Repository instructions and exact readable source/build/config/lock/wrapper state.
2. Project-native compiler/build/package/framework command when execution resolves a real ambiguity.
3. Existing IDE/project/dependency model when it is already available and more authoritative.
4. `irinse` only when selecting/configuring/operating a companion tool or verifying volatile command behavior is itself material.
5. Owning primary-source documentation for a remaining version/default/compatibility fact that cannot be established locally.

Stop as soon as the implementation-shaping fact is proved.

Record only what matters:

```text
language + version/baseline
runtime/platform when implementation-shaping
framework + version
affected modules/features
build/dependency owner
evidence identity and freshness
preview/EAP/incubator flags when relevant
consumer compatibility range for libraries
```

Do not infer a source language from a target platform (for example Kotlin/JVM does not prove Java source), a framework from a suggestive filename alone, or a project generation from current online documentation when local/native evidence exists.

## Commands are discovered, not catalogued

Do not maintain a QP table of Maven, Gradle, Kotlin, Java, Mix, Phoenix, Python, Node, Rust, Go, or future commands. Prefer project wrappers and discover the exact command from repository scripts/tasks, tool help, current official documentation, or Irinṣẹ́ when needed.

A command is unnecessary when the source already proves the fact.

## Multi-stack candidates

Load only layers that control the touched code.

```text
Kotlin + Spring + JPA
→ Kotlin + Spring guidance; framework/persistence rules specialize generic Kotlin/JVM guidance.

Elixir + Phoenix LiveView
→ Elixir + Phoenix guidance; Phoenix lifecycle/web rules specialize generic OTP guidance.

Java library with no framework
→ Java guidance only.
```

For an unfamiliar framework, do not create a new public skill merely to classify it. Pin the exact evidence available and use the bounded research policy only for questions that can materially change the implementation.
