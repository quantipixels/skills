# Core guidance

Use this condensed reference for developer documentation and technical communication in the artifact's language. Consult the linked official page when a rule is decisive, disputed, product-specific, or likely to have changed. This reference was reviewed on 2026-08-18.

## Authority and scope

- Write for software developers and other technical practitioners.
- Apply project-specific guidance before the Google guide.
- Apply the language community's grammar, orthography, tone, and accessibility conventions before English-specific examples from the Google guide.
- Prefer clarity and domain consistency over mechanical compliance.
- Keep one intended reader throughout a document.
- Describe only current, approved product behavior. Leave pre-announcements and legal claims to their owners.

Sources: [About this guide](https://developers.google.com/style), [Highlights](https://developers.google.com/style/highlights), [Future features](https://developers.google.com/style/future).

## Communication adaptation

- Apply the guide's transferable ideas to developer documentation in any language. Apply only its transferable clarity, tone, audience, terminology, and accessibility principles to other technical communication.
- Lead with the outcome, request, decision, or status. Supply the minimum context that the audience needs to respond correctly.
- Name supplied actions, owners, dates, risks, and open questions. Do not invent missing commitments.
- Separate fact, decision, assumption, recommendation, and uncertainty when their difference controls the response.
- Match the channel's length and formality. Do not force documentation headings, numbered procedures, or English person and mood patterns into a message that does not need them.
- Keep brand voice, interpersonal policy, crisis communication, legal wording, and communication approval with their owners.

## Voice and sentences

- Use a conversational, respectful, and direct tone that fits the language and audience. Avoid frivolous, pushy, or unnecessarily formal language.
- In instructions, address the reader and express commands in the clearest form supported by the language. Do not force English pronouns or imperative syntax.
- Make the actor clear when responsibility matters. Use the language's natural voice or construction when the actor is irrelevant or the object needs emphasis.
- Use the language's standard grammar, orthography, punctuation, and conventions for current behavior. Apply US English spelling and punctuation only to US English artifacts unless a higher authority says otherwise.
- Put a condition early enough that the reader knows it before acting. Use concise sentences and a natural word order for the language.
- Avoid jargon where a plain term works. Avoid idioms, slang, humor, clichés, figurative language, pop-culture references, and culture-specific assumptions.
- Do not call a task simple, easy, or quick. Apply the guide's advice about `please` only where the language and social context do not require a politeness marker.
- Define unfamiliar abbreviations on first use. Replace ambiguous pronouns with explicit nouns.

Sources: [Voice and tone](https://developers.google.com/style/tone), [Second person and first person](https://developers.google.com/style/person), [Active voice](https://developers.google.com/style/voice), [Sentence structure](https://developers.google.com/style/sentence-structure), [Write for a global audience](https://developers.google.com/style/translation).

## Documentation procedures

- State prerequisites and preparation before the task.
- Focus on the reader's goal. Prefer one short, accessible method; separate necessary alternatives.
- Use numbered steps for sequences. Use a bullet for a single-step procedure.
- Start each step with the clearest action expression supported by the language. Keep one instruction or reader decision in each step.
- Put the action before its result or justification.
- Mark an optional step with a clear equivalent in the artifact's language. In US English, Google uses `Optional:`.
- For a complex command step, use this order when applicable: action, command, placeholder definitions, command explanation, output, result.
- Do not repeat a procedure. Link to the owning procedure when the detail is nonessential in the current page.
- Avoid directional references such as *above*, *below*, or *on the right*. Refer to the named element or use *preceding* and *following*.

Source: [Procedures](https://developers.google.com/style/procedures).

## Documentation structure and lists

- Use unique, descriptive headings with the language's normal capitalization or script convention. Use sentence case only when the language and local style support it.
- Use the language's clearest action form for task headings and its natural noun construction for conceptual headings.
- Keep a logical heading hierarchy. Do not skip levels, use headings for visual styling, put links in headings, or number headings to show sequence.
- Use numbered lists for sequences, bullets for unordered sets, and description lists for term-description pairs.
- Do not create a one-item list.
- Introduce a list with enough context. Keep list items parallel and punctuation consistent.

Sources: [Headings and titles](https://developers.google.com/style/headings), [Lists](https://developers.google.com/style/lists).

## Documentation technical text and UI

- Use code font for filenames, paths, classes, methods, attributes, data types, commands, output, placeholders, and other text that readers enter verbatim.
- Use fenced code blocks for commands and samples in Markdown. Follow the project's language-specific code style.
- Keep copyable commands free of prompt symbols unless multiple input lines require context. Define placeholders near the command.
- Use bold for named UI elements. Use the element's exact visible label and add enough context when it appears outside a numbered procedure.
- Use semantic markup. Do not override the site's global font, size, or color styles.

Sources: [Text-formatting summary](https://developers.google.com/style/text-formatting), [Code in text](https://developers.google.com/style/code-in-text), [Document command-line syntax](https://developers.google.com/style/code-syntax), [Code samples](https://developers.google.com/style/code-samples), [UI elements and interaction](https://developers.google.com/style/ui-elements).

## Documentation links, media, and accessibility

- Use concise, descriptive link text that makes sense without surrounding text. Do not use *click here*, its language equivalent, a bare URL, or vague link text.
- Put essential information on the current page. Use cross-references for nonessential detail or another owner's standard.
- Prefer links that open in the current tab. Explain an unexpected download, domain change, or new tab.
- Give informative images useful alternative text. Use empty alternative text for decorative images.
- Do not place unique information only in an image. Prefer text to screenshots of text, code, or terminal output.
- Provide captions, transcripts, or descriptions for audio and video.
- Do not rely only on color, size, location, shape, sound, or punctuation to convey meaning.
- Use semantic markup, keyboard-operable controls, and a reading order that matches the visual order. Treat Google's accessibility guidance as a baseline, not exhaustive conformance proof.

Sources: [Cross-references and linking](https://developers.google.com/style/cross-references), [Write accessible documentation](https://developers.google.com/style/accessibility).

Do not use it as authority for another language's spelling, capitalization, morphology, or preferred terminology. Confirm whether an entry is general or Google-specific before applying it.
