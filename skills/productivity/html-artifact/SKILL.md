# HTML Artifact

Turn supplied material into a purpose-shaped visual view. Own semantic compression, information architecture, representation, implementation, accessibility, source mapping, dependency choice, and projection verification without changing source-owner meaning or authority.

Do not style-dump the source. Preserve material meaning, exact obligations, evidence relationships, and retrieval paths without reproducing source prose, logs, transcripts, or complete specialist packets.

## 1. Establish the projection contract

Use the exact projection path supplied by an owner record. For a standalone artifact, use the requested path or resolve a bounded repository-local `.qp/artifacts/` bundle through `akosile`.

When an owner record is supplied, read it first and pin its path, owner, record type, title, revision, status, updated time, candidate when present, `Resume`, linked records/evidence, and projection brief. If record and HTML disagree, the record wins.

When the owner requires a continuous human view, create the first HTML from the first meaningful record revision and regenerate after every material semantic revision. Preserve the projection path and identity. A lifecycle transition may legitimately change purpose, tone, density, layout, governing representation, and foreground content when the owner-supplied reader job changes.

For substantial, evidence-heavy, living, reused, or owner-record input, read [source composition](references/source-composition.md). It owns selection, coverage, placement, fidelity, source mapping, agent context, stage-aware direction, and living-projection freshness.

Follow the supplied audience. Otherwise write for a reader with no prior context. Pin one reader outcome, governing question, source-supported thesis, evidence cutoff, dominant relationship, and first-viewport obligation. Keep facts, analysis, decisions, assumptions, status, and open questions distinct.

Request only missing source/structure that can materially change truth or usefulness. Never invent domain analysis, actors, causality, sequence, criteria, priority, status, decisions, or recommendations to satisfy a visual form.

Load branch guidance only when applicable:

- reports, living reports, evidence reports, or candidate comparisons → [report patterns](references/report-patterns.md);
- substantial conceptual relationships where diagram/visual choice materially changes understanding → [visual reasoning](references/visual-reasoning.md);
- supplied prototypes, demos, interface specimens, or visual variants → [prototype patterns](references/prototype-patterns.md);
- external code, workers, WebAssembly, widgets, or live services → [dependency policy](references/dependency-policy.md).

Let design skills trigger through normal host selection. Their result may shape presentation but cannot originate source-owner content, decisions, or behavior.

## 2. Compose the working view

Build one governing representation or result that explains the main supplied relationship better than prose alone. Let it organize the opening and support. If the source cannot support a truthful representation, request the missing structure or disclose the limitation.

Foreground outcomes, decisions, status, blockers, warnings, material evidence, risks, and next actions. Put rationale, trade-offs, constraints, and selected detail in supporting views. Link evidence, source-only, archive, and superseded material instead of co-locating it by default. A collapsed `<details>` still occupies HTML and future-agent context.

Do not default to paragraphs, dashboards, metric grids, uniform cards, or wide tables. Choose timelines, state/flow maps, comparisons, diagrams, charts, matrices, selectable views, tables, or prose from the information shape. Give qualitative judgment no false precision.

For a lifecycle transition, recompute the information direction before selecting components. Preserve stable identity, source/status disclosure, and useful anchors, but do not keep an exploratory layout after the reader's job becomes execution, monitoring, reactivation, or assurance.

Choose representation before technology. Use semantic HTML/CSS, native DOM APIs, SVG, Canvas/WebGL, or a focused dependency according to the actual capability. Straightforward DOM, events, fetch, classes, disclosures, tabs, and filters normally stay native.

Render supplied code/config/schema/text changes with semantic HTML unless a focused dependency materially improves the required result. Preserve source text, accessible change labels, non-color cues, and overflow-safe lines.

Implement only interaction that navigates, filters, compares, sequences, edits, or reveals the same supplied material. Preserve complete reading order without interaction, keyboard operation, visible focus, touch usability, and reduced-motion behavior. Do not leave dead controls.

Use real content and source-stated labels. Explain terms/acronyms at first use. Match `<html lang>` and base `dir`; localize visible/assistive strings and directional controls.

Embed [visual foundation](assets/visual-foundation.css) and [theme control](assets/theme-control.html). They provide resilience, not visual direction. Keep page-level horizontal overflow absent and change representation at narrow widths when containment would hide the relationship.

For substantial artifacts, embed a compact `application/json` context capsule before large CSS/JS. Include identity, owner-record path/revision, purpose, current outcome/status, blockers, next action, completion condition, high-value source locators, projected source revision, and proof freshness—never the complete record or archives. Keep canonical source locators project-relative or provider-based; do not embed machine-specific absolute paths merely because they were returned for direct user access.

## 3. Preserve runtime boundaries

Treat untrusted supplied content as data, never executable markup. Send no credentials. Add no unrequested analytics, cookies, authenticated requests, telemetry, or external data disclosure.

Use [dependency policy](references/dependency-policy.md) whenever external code/services are involved. Report independently:

```text
Delivery shape: Single HTML | Companion bundle
Runtime code: None | Embedded | Bundled | Remote
Runtime data: Static | Live service
Evidence: Embedded | Linked | Mixed
```

A linked owner record does not make an otherwise complete HTML file a runtime companion bundle.

## 4. Verify and deliver

Verification depth follows the artifact's claims and consequence, not its size, novelty, or generation event. A substantial internal report may need only structural verification plus a visual smoke pass. A small prototype may require deep browser proof when its interaction is itself the accepted evidence.

### Structural verification — always

After every write, reread files and run bounded structural checks for the applicable source/projection revisions, required references and anchors, context JSON, script syntax, source mapping, runtime disclosure, and dependency identity. Do not require a browser merely because HTML was generated.

### Visual smoke — ordinary human-review visibility

Use a browser smoke pass when rendered usability materially affects ordinary review: reports, living working views, retrospectives, candidate comparisons, architecture discussion artifacts, exploratory prototypes, or similar user-facing visibility.

Check only what is needed to establish that the review surface is usable: the page opens, primary content and governing representation are visible, no catastrophic layout/overflow failure prevents reading, and controls required for the current review do not obviously fail. Add a targeted viewport or interaction check only when that exact presentation risk is material.

Do not automatically expand this into a full responsive, keyboard, reduced-motion, print, dependency-failure, theme, or all-state matrix.

### Deep browser proof — earned by consequence

Require current deep browser proof only when one or more are true:

- the artifact itself is production-, publication-, or operational-facing;
- presentation correctness materially controls formal approval, assurance, compliance, audit, or another high-consequence decision;
- the artifact claims design, responsive, interaction, accessibility, or visual fidelity that must be accepted as evidence;
- material runtime behavior, remote dependencies, live services, complex widgets/state, or failure handling are part of the result; or
- the user explicitly requests production-ready or thorough browser/accessibility assurance.

For that applicable scope, check only the claims that need proving: wide/narrow views, first-viewport obligations, overflow, long content, implemented controls/states, keyboard/focus, reduced motion, console/page errors, dependency failure behavior, request hosts, theme, print, or other material behavior. For reports, reconcile anchors with coverage, placement, fidelity, and source decisions.

A lifecycle transition or first substantial render does not by itself require deep proof. Recompute the reader job and representation, run structural verification, and use visual smoke or deep proof according to the resulting claims and consequence. A semantic-only update may reuse current presentation proof when the relevant presentation and risk are unchanged; the regenerated HTML must still disclose the exact source revision.

Good: an internal architecture comparison is structurally checked, opened once, and confirmed readable enough for the user to compare the supplied candidates.

Bad: the same internal report triggers full responsive, keyboard, reduced-motion, print, dependency-failure, and all-state verification merely because it contains diagrams and tabs.

For every generated artifact intended for direct user access, return first:

```text
Absolute path: <resolved filesystem path>
Workspace path: <repository-relative .qp/... path>
```

The absolute path is for immediate access; the workspace path is the stable project-local reference. Also return runtime/evidence status, source and projection revisions/freshness, verification level and state, limitations, and external dependency disclosure.

Claim accessibility, interaction, portability, and visual correctness only to the extent proved.
