# Set up Alárinà for a project or environment

Establish the project's philosophy, an adaptable development lifecycle and the capabilities Alárinà needs to work effectively, or configure the requested personal environment. Setup is optional: ordinary tasks discover what they need without first running this command. A working setup can return a no-change result. A readiness assessment remains read-only; a setup request permits the relevant configuration and instruction edits, preserving unrelated preferences and existing authority boundaries.

## Discover the missing agreement

Start with the requested scope. Project setup concerns shared project expectations and working capabilities; environment setup concerns the user's host, tools and preferences across projects. Inspect the affected scope, not every project or installed capability.

Read the [engineering boundaries](../references/engineering/policies.md) and [configuration contract](../references/productivity/environment/configuration.md). Reuse current instructions and evidence. Follow existing pointers to standards, architecture, `CONTEXT.md` or scoped glossaries, ADRs, non-goals, contribution guidance and the project's tracker. Read the bodies and applicable linked procedures, not just their names. Locate the actual build, local gates, CI requirements, verification recipes and active host review/delegation capability. Identify artifact destinations through [records](../references/productivity/records.md), including the effective `doc_root` and isolated project/task state.

Run `alarina.py doctor --project <checkout>` for read-only configuration and prerequisite facts. Inspect its proposed command sources before use; `configured` is not executed proof. If local gates or assembled-product verifiers are missing, explicitly advise the user what is missing, which outcome it leaves unproved and the smallest useful local path. CI must not become the first place ordinary defects are discovered. During authorized setup, establish and exercise that local path; genuinely remote-only proof stays a separate obligation.

For unresolved project-readiness questions, use [sawari](sawari.md) to map the relevant repository behavior, owners, documentation and working/verification paths. Use the [agent-respondent perspective](../references/productivity/inquiry/agent-respondent.md) to interrogate that map with accepted project decisions. Reuse sufficient current understanding instead of requiring a full survey or interview on every setup.

For project setup, read [project philosophy and SDLC adaptation](../references/engineering/development-practice.md). Discover the project's purpose, governing principles and consequential trade-offs from its evidence, then use [arojinle](arojinle.md) with the actual user for unconfirmed intent or priorities that control the setup. Keep observed habits distinct from confirmed philosophy; the agent cannot answer those human choices on their behalf.

Use that agreement to assess the project's path from framing and design through implementation, verification/review, release, operation/recovery and learning. Identify the missing capability or agreement and its smallest useful correction, including how the agent can make and undo changes within authority. Configure the needed depth and feedback for this project rather than imposing every stage on every task. Personal-environment setup alone does not establish project philosophy or release policy.

For project setup, establish the [useful documentation baseline](../references/engineering/documentation/project-baseline.md) from that understanding, including missing architecture, standards, confirmed non-goals and working instructions where they earn a home. Use [akowe-sync](akowe-sync.md) to reconcile the set through its existing owners; consume its result here. Personal-environment setup alone does not create project documents.

For a missing reusable way to exercise and observe the project, use [alaga-verify-project](alaga-verify-project.md), reusing adequate commands and harnesses first. For missing or unclear agent-facing instructions, use [oro-sigidi](oro-sigidi.md) with discovered or verified facts and the existing instruction owner.

Consume sufficient existing results without reopening those methods. The supporting command returns its evidence or gap here; it does not start a second setup, initiative or publication workflow.

Read [CI/local equivalence](../references/engineering/verification/ci-local-equivalence.md) when establishing the project's local path. Map relevant CI obligations and material environment differences to actual local proof or a named remaining obligation. A configured gate and a healthy doctor cannot reveal every omitted job. Keep the mapping with the existing verification/build instructions and refresh only affected entries.

## Configure only what will be consumed

Keep shared expectations and verification instructions in their existing repository owner. Add a short entrypoint pointer when needed. During project setup, register the selected real commands, their proof formats, required tools, existing policy sources and remote-only checks in `.alarina.json`; reference existing runner implementations instead of duplicating them. Set `doc_root` only for an established project artifact convention, otherwise use the record policy's isolated task artifact directory. Configure shared workflow roots only when they contain actual reusable recipes. An already sufficient configuration can remain unchanged; an assessment-only request reports the proposed delta without writing it. Do not create duplicate standards or placeholder verifiers.

Keep personal model, effort and subagent preferences in the user's global/project instructions and supported host settings. The [delegation example](../references/productivity/environment/delegation-example.md) shows an adoptable brief using Luna, Sol and Astra without prescribing a roster; offer or adapt it when requested, preserving existing preferences. Read [host policy](../references/productivity/environment/host-policy.md) when controls need changing. Personal storage and opt-in contribution suggestions use the personal configuration layer. An available model is not an obligation to assign a worker, and a preference file does not prove activation. Explicit-only `pese` and `qp-update` retain their invocation rules.

Establish the local path to [delivery and publication readiness](../references/engineering/delivery/local-readiness.md): relevant checks, independent review, shared criteria and genuinely remote-only proof. Exercise the selected commands with `alarina.py verify` when their effects are authorized; inspect actual test counts and check results. Persist reusable invocations and expected observations; keep transient health evidence in the task's private check record. Do not freeze a green status into policy. Use [standards applicability](../references/engineering/verification/standards-profiles.md) for an adopted external standard. A missing prerequisite is a named gap, not authority for unrelated installation, live effects or product repair.

## Verify and return

Exercise a changed verification capability through its owning method. For instruction-only changes, check the affected reader path and the accuracy of its commands and pointers. For host changes, distinguish files written from settings actually loaded. Reuse current proof and refresh only what setup changed; no full project audit is required.

Finish with the confirmed project philosophy and applicable lifecycle choices, what is usable, the owners changed or reused, decisive verification and remaining prerequisites. Include only the requested project or environment scope. Setup is complete when the scoped working path is established and relevant configuration works; unresolved governing choices, unexecuted recipes or unavailable review remain explicit gaps. Return a concise result, not a setup report by default.
