# Adversarial and council review

Read when an Àtúnwò review has a consequential disputed claim, a plausible failure mechanism that ordinary inspection has not settled, or materially different expertise needed to judge one candidate. These are optional ways to strengthen the same read-only review, not separate acceptance authorities. A bounded change with clear evidence needs neither. Review depth still follows Àtúnwò; a request for light or time-bounded review does not silently expand into a council.

## Challenge a consequential claim

An adversarial pass argues the strongest plausible countercase to the current conclusion, whether that conclusion is a finding or a clean result. Start from the pinned candidate, accepted requirement, actual execution path and existing safeguards. State the claim's necessary conditions, the concrete observation that would falsify it, and the cheapest available evidence that could distinguish the competing explanations. Inspect counterevidence with the same care as supporting evidence. For a claimed defect, a realistic input and reachable effect matter more than a hypothetical failure story; for a claimed safeguard, verify that it covers the relevant path and conditions.

Return a supported finding, narrowed finding, rejected claim, or explicit proof gap with locators. Do not invent a defect to satisfy a challenge, count disagreement as evidence, or turn uncertainty into a severity label. A proposed experiment is not executed proof. Keep reviewed source, Git state and provider state read-only; fault injection, mutation of fixtures or services, and other disruptive experiments need separate authority and an appropriate owner. Use safe, authorized inspection or bounded checks when they can settle the claim; otherwise return the discriminating proof to the change owner.

## Convene distinct expertise only when it helps

A council earns its cost when independent perspectives cover materially different risks or a consequential disagreement remains after a focused pass. Choose perspectives for the actual uncertainty, such as domain behavior, architecture, security, operations or test adequacy. Do not assemble a fixed roster, duplicate the same review, or select models and effort here; user and host policy own those choices. One capable independent reviewer is sufficient for ordinary delivery readiness.

Cap each council at **three agents total, including the main agent**: at most two specialist reviewers. Reuse those participants for a justified follow-up; do not add a separate judge, synthesizer or replacement roster to expand the council. Narrow or sequence the questions within that cap. The main agent's coordination or authorship does not count as independent acceptance of its own work.

Brief each reviewer with the same pinned candidate and comparison base, accepted behavior, scope, authority and available proof. Give each the relevant standards or domain sources, and request an independent first judgment before sharing other reviewers' conclusions. A reviewer who authored a portion cannot independently accept that portion. Parallel reads require a stable candidate and respect coordination's shared-resource boundaries.

The main agent compares claims by mechanism, source identity, assumptions and evidence. Deduplicate agreement; for a material disagreement, inspect the disputed path or run one targeted, authorized check that can distinguish the claims. Do not vote, average severity, or treat reviewer count as proof. If the disagreement is a user-owned priority, requirement or risk choice, present the evidence and consequence to the user. The main agent adjudicates technical findings and owns the resulting recommendation; reviewers supply evidence, not authority.

## Bound and refresh the work

Begin with one focused challenge or independent first pass. Add a targeted follow-up only while it can resolve a named material uncertainty; stop when decisive evidence settles the claim, the remaining gap belongs to the change owner or user, or another round would only repeat positions. Record actual coverage and unresolved proof rather than promising exhaustive consensus. Extra review must justify its briefing, execution and integration cost.

Tie conclusions to the candidate/base and requirement version reviewed. If edits, generated outputs, the base or accepted behavior change, identify which conclusions depend on the changed material and refresh only those. A stale conclusion cannot accept the new candidate. The owner integrates warranted corrections, verifies affected behavior and seeks focused rereview where the correction or contested claim demands it. Preserve valid evidence for untouched paths and retain Àtúnwò's separate Standards and Specification conclusions and acceptance vocabulary.
