# Test-suite improvement

Use when an existing suite is slow, brittle, redundant or weak at detecting required failures. A single known test defect can go directly to `alaga`; establishing a reusable assembled journey uses Project verification.

1. For an audit-only request, give `atunwo` the suite and proof question, use `irinse` for needed measurements within that read-only scope, and stop at findings. For an accepted improvement, give `alaga` the affected suite, observed cost or maintenance problem and required behavior. Its test-suite improvement method establishes the actual baseline and current proof owners.
2. Use `atunwo` for independent judgment of suspected weak or duplicate proof. `irinse` supplies a bounded measurement or mutation campaign when it can settle a concrete uncertainty; tool scores do not decide which tests go.
3. `alaga` repairs, consolidates or removes justified tests and verifies the retained obligations. Use `architect` only when a structural testability problem controls the change.
4. Reuse the affected real API, persistence and assembled-journey proof. If a claimed speed improvement needs comparison, `adanwo` measures compatible workloads; reduced test count alone is not the result.

Finish with the retained behavior, changes and evidence of the requested improvement. Identify any obligation still lacking proof. Quarantining a flaky check or deleting a failing assertion does not establish that its behavior is now protected.
