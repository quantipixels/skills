# Engineering maintenance

Use when a project needs a bounded improvement to engineering readiness, agent instructions, verification capability or an adopted workflow. Setup establishes the baseline; this playbook closes observed gaps and maintains it over time. A read-only assessment stops at findings. Ordinary feature delivery keeps its existing owner.

At the project’s regular maintenance review, reconcile CI expectations through [CI/local equivalence](../references/engineering/verification/ci-local-equivalence.md): compare current obligations, local proof, actual CI coverage and provider-required checks. Reuse the last reconciliation for unchanged boundaries; record drift, its owner and the next review trigger at the existing verification/build owner. Scheduling remains a separately authorized effect.

1. Establish the named project, requested finish, actual instructions and affected working path. Read [engineering boundaries](../references/engineering/policies.md), then [alarina-setup](../commands/alarina-setup.md) for baseline assessment. Use the read-only doctor to inspect registered commands, policy sources and storage. Read the actual methods, scripts and consuming configuration behind consequential claims. Explicitly report missing local gates or verifiers; do not infer readiness from CI or configuration presence.
2. Prioritize a concrete failure or repeated cost with available evidence: misplaced records, stale instructions, unproved checks, weak feedback, duplicated workflow steps or failed cleanup. Use [ayewo-retro](../commands/ayewo-retro.md) for session evidence or [ayewo-corpus](../commands/ayewo-corpus.md) for a requested bounded corpus. Neither a report's gap count nor another plugin's feature count proves a need. Select a useful expected outcome and a failure case that would falsify it.
3. Within requested remediation scope, have [alaga-deliver](../commands/alaga-deliver.md) implement the smallest coherent correction. [alaga-verify-project](../commands/alaga-verify-project.md) owns reusable verification capability, [oro-sigidi](../commands/oro-sigidi.md) owns agent instructions, and [akowe-sync](../commands/akowe-sync.md) reconciles affected project knowledge. Register real local commands and evidence adapters through [configuration](../references/productivity/environment/configuration.md). Keep user-owned delegation preferences in `AGENTS.md` or the native equivalent. Do not silently change provider permissions or install global tooling.
4. Exercise the changed path from its documented starting state, include the selected failure/recovery case, and apply [local readiness](../references/engineering/delivery/local-readiness.md). Require independent [atunwo](../commands/atunwo.md) review for substantive changes. For behavioral instruction claims use the [skill-evaluation](skill-evaluation.md) playbook at the affected boundary. Separate structural validity, actual execution and model behavior; describe untested environments honestly.
5. Adopt a proven reusable sequence through [learned workflows](../references/productivity/learned-workflows.md). Reuse or revise its existing owner, keep project-specific knowledge in that project's library, and qualify portability from evidence. Retain useful proof before cleaning owned processes, temporary data and obsolete recipes under [records](../references/productivity/records.md). Preserve unrelated work and report cleanup failures.
6. At a meaningful adoption boundary, compare observed benefit, challenges and remaining cost. Revise or retire a path that no longer earns its upkeep. If the user requests recurring maintenance, deploy the bounded on-demand recipe through the host's native scheduler with explicit project scope, authority, overlap/resume handling and actionable notification conditions. Scheduling is a separate authorized effect. When contribution suggestions are requested or enabled, use [contribution guidance](../references/productivity/contributing-improvements.md) for a local, synthetic proposal and its review; publication retains its own authority.

Finish with the corrected capability, canonical locations and invocation, actual proof, adoption/cleanup state, and material limits. An assessment, an unexecuted recipe or a privacy scan alone cannot establish a mature engineering outcome.
