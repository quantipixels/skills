# Skill evaluation and improvement

Use when retention of a consequential skill, instruction or routing change depends on actual comparative outcomes. Ordinary wording fixes go directly to `oro`; a request to evaluate ends at the supported result unless adoption is also authorized.

First name the unresolved decision. For script mechanics, use `alaga` and a direct execution check with representative safe inputs. Routine `qp-update`, `system-cleanup`, `pese` and similar utility work needs no standing model-eval pack. A targeted probe is justified by a concrete model-dependent failure or material authority/behavior change, not merely the existence of a skill. Do not run real updates, destructive cleanup or external serving just to test instructions.

1. Name the decision, behavioral failure or risk and expected effect. Resolve an unexplained failure through the existing diagnosis or postmortem owner before choosing a remedy. Use `oro` to author or revise the exact instruction candidate.
2. Use the project's existing evaluation process. If none exists, bound this comparison: freeze candidates, tasks, acceptance and budget; hold unrelated model/tool conditions compatible; use fresh sessions and keep private criteria out of actor inputs. Include a useful control and distinguish synthetic probes from observed failures. Native hosts own execution, isolation and worker lifecycle. Supplying guidance does not test its discovery.
3. Consume actual artifacts and execution evidence. Prefer executable acceptance; a model judge used at scale needs validation against qualified human labels, including separate missed-failure and false-alarm checks. A structural check or routing answer cannot establish end-to-end improvement. Keep invalid trials, missing access, failures and inconclusive differences visible.
4. Return the supported retain, reject or inconclusive result. With adoption authority, `oro` finalizes instructions; refresh only comparisons invalidated by the finalization. Installation and publication remain separately authorized.

Finish with the exact candidates, observed benefits/costs, limits and adoption state. Do not turn a one-off smoke check into a permanent benchmark by default. A supplied-candidate success does not establish native discovery or installed-host execution.
