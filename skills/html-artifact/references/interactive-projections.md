# Interactive projections

Use when coordinated views, a guided sequence, a supplied-model demonstration or reader feedback materially improves usefulness. Start with a faithful static representation; add interaction only to inspect supplied relationships, reveal a model or return a precise response.

Define stable view/item identities, governing questions, directed relationship meaning, guided targets, source attachments, coverage and freshness before choosing a renderer. Layout and runtime state may position, select, filter or navigate; they cannot invent causality, ownership, priority, findings or sequence. Keep content escaped and inline for standalone local artifacts where adjacent-file fetching would fail.

Use native browser primitives for a small bounded view and a current focused renderer when it materially improves correctness or interaction. Bundle or staticize standalone dependencies, preserve a semantic fallback, and keep lane-specific data/style separate from the reusable capability.

Controls must expose current state, direction and persistent detail; support keyboard, focus, touch, narrow widths, reduced motion and printable reading order. Filtering changes visibility, not meaning, and needs a clear reset/result state.

For supplied models, pin rules, input domain, units, assumptions and baseline. Show what changed and why; calculated output is illustrative, not observed proof. For feedback, export artifact identity/revision, stable targets and proposed changes with visible copy/download status. Selection or an “approve” label neither updates the canonical source nor grants authority; the owning workflow reconciles stale replies.

Verify identities, endpoints, guided targets, escaped data, dependency identity and absence of unrequested hosts. In a browser, exercise only the material claims introduced: selection/detail sync, filter/reset, known model case, exported revision/target or failure fallback.
