# Bundled script boundary

Read when adding or changing executable capability after considering resource placement.

Keep code when a bounded mechanical result has a real consumer and packaging materially improves correctness, reuse, or safe invocation over available tools. Examples include an exact validator/transform or lock-held compare-and-swap publication.

The script must own that mechanical result, have tests that can falsify it, and leave interpretation, routing, acceptance, and authorization with the agent or responsible skill. Repository/provider/runtime truth stays authoritative. Introduce state, locks, retries, schemas, or daemons only for a demonstrated need.

Ordinary search/filter wrappers, Git/filesystem recipes, provider normalization solely for model consumption, and executable lifecycle checklists generally add machinery without earning it. Keep an engine only when it carries a substantial deterministic part of the result rather than assembling convenience wrappers.

A public install/bootstrap/uninstall helper has a different justification: one safe, stable user entry point. Keep it transparent, conservatively scoped, and native-tool-backed without parallel semantic state.

Explain whether to keep, shrink, replace, move, or remove the code and why. Name the retained mechanical contract and its proof; do not generate a separate report or impose a disposition schema unless a consumer requires it.
