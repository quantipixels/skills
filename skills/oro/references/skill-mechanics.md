# Skill mechanics

Read only when the agent-facing artifact is a skill. A skill packages an independently useful semantic result or method; start from that result rather than a taxonomy.

## Identity, invocation and ownership

A public skill needs a realistic direct trigger, nearby exclusions and a reason the behavior is more coherent here than in an existing owner. Different subject matter or file length is insufficient. Keep directory/frontmatter identity and invocation metadata consistent; preserve existing permissions unless the requested change deliberately alters them.

Model-reachable skills spend routing context and human-invoked skills spend user memory. Use current host controls, keep descriptions discriminative, and narrow compatibility aliases so they do not compete with their replacement. Distinguish source presence, valid installation, host discovery and active invocation; proof of one does not establish the others.

Reference stable public owners by exact skill name and add only the useful mode or constraint. A router preserves route topology and adjacent-owner distinctions while installed definitions supply dynamic inventory; do not replace topology with description matching or rebuild an exhaustive catalogue.

## Keep layers distinct

A skill owns reusable semantics. A workflow owns progression. An assignment defines one delegated result, context, authority, evidence, independence and stop condition. A provider-native agent definition is optional only when a recurring tool, permission, isolation, model or runtime delta cannot be expressed through the assignment or native controls.

Use `irinse` for host declaration setup and verification. Preserve unrelated user configuration and actual provider precedence; a definition value may be a pin rather than an overridable default. Keep portable semantics in one place and host adapters thin. Do not add durable role fleets or copy native spawn/wait mechanics into a skill.

## Resources

Keep a reference when it changes a recurring non-obvious decision and has a reliable load condition. Remove copied volatile documentation, cheap facts and task history. Split on independently selectable branches, not line count.

Keep bundled code only for a bounded mechanical result that improves correctness, reuse or safe invocation over native/project tooling. Shipped code needs falsifiable tests for realistic failure. Interpretation, acceptance, routing and authority remain with the owning skill; avoid wrappers for ordinary search, Git or filesystem recipes.

Keep templates when a stable recurring shape prevents meaningful omissions, and data only with a freshness boundary that supports the result. For host adapters, preserve package-owned assets, user settings and invocation permissions. Treat provider precedence as provider-specific.

## Evolution and proof

For a portfolio review, compare public identities, owned results, routing collisions, aliases, always-loaded context and representative end-to-end paths. Counts and lexical overlap are leads, not redundancy verdicts. Use real selection/value/boundary evidence where available; missing historical evidence remains a gap, not a permanent veto.

Validate selection, loading, authority and behavior according to what changed, then run the package's actual structural validation. Package syntax alone does not prove routing or behavior. For a material refactor, classify semantics as retain, strengthen, relocate, replace or retire and confirm deleted resource names no longer remain as active instructions.
