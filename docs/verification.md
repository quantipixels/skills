# Verify the capability being claimed

Package checks prove discovery, references, and mechanical behavior. They do not prove that an authenticated model selects or applies a skill. Use a fresh host session for a changed behavioral claim and record the exact candidate, host/version, model/settings when observable, actual actions, and evidence limits in the PR or CI.

Do not inject these acceptance notes into the session as if they were skill instructions. A meaningful before/after comparison uses the same task, evidence, permissions, and host configuration. The baseline need not fail: ordinary host capability can already be adequate. Retain a standing behavioral regression only for a recurring, stable risk.

## Small native-host check

Select the installed Pepeye entrypoint. Ask a simple factual or explanatory question, then request a bounded specialist result. Check that ordinary work is handled directly, the relevant installed skill is actually applied when useful, and neither an unnecessary router nor another agent is required. Skill names in the response alone are not evidence of application.

Use an interactive decision-tree task whose vocabulary has a consequential distinction. Confirm that Àròjinlẹ̀ uses Amọ̀ṣẹ́, resolves facts without unnecessary user questions, tests meaning and choices in the same conversation, recomputes dependent questions after answers, and waits for user confirmation. Do not require a model delta, document, or write when there is no need or authority.

Request two independent read-only checks and a related follow-up to one worker. Observe early guidance, actual handle reuse, sufficient evidence, and honest model/effort and status reporting. Cancel a worker and redirect a goal; affected work must stop or be updated without restarting the cancelled run. Without delegation capability, report the limit instead of inventing a team or background monitoring. Resume/compaction does not prove that old handles remain live.

For a changed delivery path, use a disposable repository and test-only data. Require a bounded implementation, evidence that can falsify it, and genuinely independent review where required. Check that scope, unrelated files, publication authority, and the exact reviewed candidate are preserved. A code change, a passed test, a merged feature branch, and a released version are separate facts.

## Other changed boundaries

Use only the relevant cases. An obvious review does not need triage and diagnosis first. A guard-only or human-led review request does not authorize edits. A spec or architecture answer needs formal readiness only when that result is required. A postmortem with authorized remediation must reuse the reconstructed evidence and complete that requested work rather than stop after analysis.

For provider/stack work, challenge base movement, merged-parent ancestry, outdated check results, unresolved feedback, untrusted provider content, and loss of access. Refresh the affected candidate/proof rather than guessing integration from a PR label. Respect explicit-only activation such as `pese`; implicit intent is not permission to bypass that metadata.

For Kọ, distinguish a missing/ambiguous instruction from an ignored rule, a discovery mistake, a tool failure, or ordinary model variance. No change is valid. New public identities need a credible positive and adjacent-negative selection case; Experimental is not proof of promotion. Preserve a useful rare capability without imposing invocation quotas.

These are reusable checks for current capabilities, not a mandatory pipeline, benchmark score, or replacement for skill-specific proof. Unavailable authenticated sessions remain `NOT_RUN`; do not fill the gap with a keyword assertion or a simulated transcript.
