# Keep plan tickets local

QP will add `seda-ticket` as the reusable owner for a checked local ticket graph derived from stable plan phases and review candidates. Atona retains plan identity, decisions, readiness, delivery milestones, integration acceptance, and closure. Alaga retains internal feature tasks, TDD slices, proof, and delivery procedure.

For ticket-backed delivery, `seda-ticket` creates or reconciles stable plan-scoped IDs, phase parents, candidate children, explicit dependencies, cycle checks, stale markers, and optional Git evidence already supplied by a delivery owner. Stable owner-supplied phase and candidate keys control ID preservation and supersession. `seda-ticket` prepares and validates the ticket-section replacement; `html-artifact` owns the atomic physical edit for an Atona HTML plan; then `seda-ticket` verifies the returned exact artifact. Atona verifies the graph before it marks the plan `Planned`.

The first release is fully local. It has no provider adapter, remote identity, authentication, pagination, external read, or external write. A later provider projection requires a new architecture decision. The ticket workflow also defines no Git operation; it may only retain exact-current Git evidence produced by an owning delivery workflow.

This separates reusable local ticket-graph policy from Atona without creating a second ledger or moving plan or artifact authority. Phase parents store graph identity, canonical phase reference, child membership, and graph lifecycle. Candidate nodes store graph identity, canonical candidate reference, parent membership, candidate dependencies, and graph lifecycle. Neither copies authoritative plan or delivery state. Candidate-to-candidate edges are the only dependency edges. The nodes bind to the source semantic plan revision; the resulting whole-artifact digest is returned separately. It accepts one additional skill handoff and the need to prove that `seda-ticket` is deep enough to justify a public owner. If stable identity, hierarchy, dependency validation, cycle detection, stale reconciliation, and checked local updates do not remain behind a small interface, the skill must not be published as a shallow pass-through.
