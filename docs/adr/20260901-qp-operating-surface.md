# Keep the QP operating surface thin over deep owners

Status: Accepted

QP will grow capability depth faster than public surface area. The user-facing interface is a small set of independently useful owners; owner-local references, tools, and supporting methods remain behind those owners unless a separate public identity materially improves direct selection, authority clarity, result identity, or reuse.

## Entry

Use an obvious exact owner directly. Use `alarina` only when the correct owner is genuinely unclear, the user asks for portfolio routing/inventory, or several independently useful owner results require sequencing.

Generic `Use QP` intent grants no additional lifecycle, mutation, provider, review, publication, credential, or destructive-action authority. Routing stops once semantic ownership is clear and does not expose an owner's internal support topology.

## Composition

Each owner keeps its own outcome, authority, procedure, result shape, proof, recovery, and completion boundary. Callers pass only the bounded context/result needed across a real ownership boundary.

A capability may remain deep without becoming public. Candidate-pinned implementation counsel is an Alága path; exact-version upstream source grounding is an Ìwádìí escalation. Their useful behavior remains available without separate Akọ̀wé or Orísun public selectors.

Semantic decomposition and operational containers are independent. Requirements, tickets, phases, proof obligations, and capability boundaries describe meaning; commits, branches, candidates, PRs/MRs, test files, browser runs, and agent sessions are chosen for integration, review, rollback, ownership, release, or evidence value rather than mapped one-to-one by ceremony.

## Host projections

A host adapter may make the portfolio easier to enter, but it is not another semantic owner. It may select or invoke existing owners while preserving their normal trigger, authority, safety, host-invocation, and completion contracts.

The optional Claude Code QP agent therefore preloads only `alarina` and remains a thin host projection. It does not own task state, proof, acceptance, memory, publication, review, or durable project knowledge. Direct skill invocation and hosts without this adapter remain first-class.

## Experimental maturity

Experimental is a maturity/evidence group, not a blanket routing exclusion or automatic acceptance tax. An Experimental skill receives normal runtime opportunities when its own trigger, authority, cost, safety, and host-invocation boundaries are satisfied.

Promotion requires both recurring capability value and useful independent public identity. A method that proves valuable may still correctly be folded behind an existing owner when that preserves its benefit while reducing public/routing surface.

## Design convergence

Design direction remains with `amoye-ui-ux`; React/web implementation and native proof remain with `asa-oju-ibanisoro`.

When a material design choice is open, explore only materially different mechanisms after freezing accepted product and brand constraints. When a visual reference controls acceptance, distinguish semantic capability from visible and interactive affordances. Final design judgment uses exact rendered evidence rather than source-code intent and stops when no material deficiency remains.

## Rejected alternatives

QP will not add a shared `qp-mode`, orchestration runtime, copied owner catalogue, mandatory public pipeline, or another durable state/proof layer merely to connect skills. It will not keep support-shaped public skills solely because their underlying method is useful, and it will not project ticket or requirement boundaries mechanically onto Git/review/test/session topology.

## Consequence

The portfolio may deepen substantially without requiring users or routers to learn a correspondingly larger set of names. New public skills must earn both capability value and public-identity value; new host integrations must remain projections over canonical owners rather than becoming competing architecture.
