# Project verification

Use to establish a reusable way to exercise the assembled application, or maintain verification knowledge after the product changes. An ordinary change with adequate existing checks stays with [alaga-deliver](../commands/alaga-deliver.md).

1. Inspect applicable project instructions, installed project verification skills and existing commands. Reuse the working capability and its real public boundary. A missing custom driver is not itself a gap when native commands suffice.
2. [alaga-verify-project](../commands/alaga-verify-project.md) owns the project-verification method, any needed harness implementation and the executed journey. Resolve non-obvious capability or readiness gaps through the project and host. Use [oro-sigidi](../commands/oro-sigidi.md) when reusable instructions or a project-local skill are requested or needed; supply verified commands and evidence for the writing.
3. Exercise a representative authorized journey with observable effects and owned-resource cleanup. Reuse current evidence and retain the result after teardown. Missing runtime access leaves an unexecuted recipe, not a working verification capability.
4. For maintenance, distinguish stale instructions, a harness limitation and a product regression. [oro-sigidi](../commands/oro-sigidi.md) corrects the instruction, [alaga-deliver](../commands/alaga-deliver.md) fixes authorized harness/product defects, and the verification owner re-exercises the affected path. Do not erase an expectation to hide the regression.

Return the reusable invocation or exact commands, exercised boundary, evidence and remaining limits. A scoped maintenance request covers affected journeys; a full-map audit covers the requested map. Project-local authoring does not silently install global skills, add dependencies or change host configuration.
