# Coding-agent/session postmortem

Use for a coding-agent session, rollout or agent-mediated delivery.

Pin repository/candidate identities, instructions/skill versions, tools/environment/context/authority and request revisions that evidence shows were available at each material action. Hidden reasoning, current source and later summaries do not prove historical knowledge. History/reflog may correlate state with timestamps but has local, expiry and rewrite limits.

Verify consequential completion/mutation claims against the corresponding candidate or external state when available.

## Distinguish the failure

Classify the smallest supported cause:

- missing or ambiguous rule;
- violation of a clear available rule;
- tool/environment or context/attention failure;
- authority or evidence gap; or
- reasonable decision later made obsolete.

For overengineering claims, require contract-relative evidence such as unplanned dependency/public-contract growth, speculative abstraction/configuration, parallel implementations, production seams created for shallow tests, repeated fixer machinery, mirrored/mock-choreography proof, or attributable later deletion/rework. These are signals until the historical contract shows the expansion was avoidable.

Do not propose a skill edit merely because an agent erred. A skill-body change requires an active selection/instruction gap and a reusable rule likely to prevent the evidenced failure. Clear-rule violations, unavailable tools and ordinary variance call for their actual owner.

## Improve the actual system first

Locate friction in navigation, deterministic enforcement, review standards, always-loaded steering, tool economy or information access. Inspect the relevant task context before interpreting structural session counts.

For a missed mechanical error, inspect the project's actual lint/typecheck/test commands and their CI or hook wiring before proposing another check. Distinguish absent enforcement from an existing check that was skipped, misconfigured or silently ineffective. Recommend repairing the existing owner when it covers the failure. A new rule should reject the observed violation through the cheapest appropriate project mechanism; a judgment-dependent concern belongs in review guidance.

Separate construction constraints from review expertise when context pressure contributed. Keep requirements, invariants, authority and compatibility constraints available to the implementer. Put detailed judgment-based standards with the review method and load them at review; do not repeat its whole checklist in every implementation prompt or global `AGENTS.md`. The reviewer may still need to trace consumers and context beyond a diff. Use the actual evidence, not a blanket assumption that reviews are cheap.

Prefer the smallest effective owner: project/runtime enforcement; authoritative access/navigation; independent review policy; narrow skill/reference; then always-loaded instructions only for cross-task behavior. Safety and authority rules remain independently loaded.

For any durable change state the observed friction, owner, smallest change, expected effect and later falsification. Prefer remove, move, mechanize or sharpen over appending prose. Record no instruction change when the existing contract was adequate.
