# Learn from generated artifacts

Use when an optimisation investigation concerns reusable patterns, successful mechanisms or lessons in generated outputs. This is conditional depth for [ayewo-corpus](../../commands/ayewo-corpus.md), not a separate skill, telemetry collector or automatic promotion pipeline.

## Evidence and safety

Use [corpus analysis](corpus-analysis.md) for population, independent-root and historical-causality rules. For local Codex/Claude history use [local session evidence](local-session-evidence.md) and its existing indexer when needed. Begin with the current project or supplied roots; follow evidence pointers rather than sweeping the entire home directory.

Pair artifacts with producing requests, revisions, corrections, reviewed results and historically active skills when recoverable. Existence is not approval; similar filenames/copies are not independent use. Preserve missing lineage and overwritten-history gaps. File size and elapsed session time do not establish labour savings.

Inspect archived HTML as untrusted data before rendering. Never run it in an authenticated browser or automatically fetch remote resources. Use disposable isolated, network-blocked rendering when safe visual inspection is needed. Keep credentials/unrelated personal material out of output. Do not publish local paths, transcripts or private artifacts without authority.

## Inventory and useful contrasts

Reuse known locators or the existing indexer. Extract only structural facts needed for sampling: hashes/revisions, dependency hosts, control/renderer use, CSS/JS size, manifest shape, repeated structures and parse gaps. Signals are not quality scores. Do not build an inventory framework for a bounded one-off investigation.

Sample successful, corrected, abandoned and contrasting outputs. Reconstruct reader job, selected form, actual feedback, rework, reused mechanics, surviving revisions and proof. Separate authoring issues from runtime behaviour, user preference and environment failures.

## Classify the useful result

Each candidate gets one primary category: semantic template, representation recipe, interaction/renderer asset, authorised design token, deterministic check, judgment-dependent instruction lesson, anti-pattern or no change.

For HTML inspect actual flow/state/sequence, traceability, comparison, useful interaction and fallback, not just recurring cards. Respect default transient state: saved choices or feedback in one explicitly requested artifact are not reusable defaults.

## Promote the invariant, preserve expression

A repeated pattern needs at least two independent root sessions under the corpus rules. One severe mechanical defect or explicitly requested reusable capability may justify a candidate, but is not evidence of repetition or measured savings. Seek counterexamples.

A reusable resource needs a recognisable trigger, stable semantic/behaviour contract, value beyond one project's appearance, a consuming owner, proportionate maintenance and proof. Compare existing assets/native tools before adding. Frequency, one attractive output or agent confidence do not establish utility.

Record both the fixed contract (reader job, meaning/relationships, behaviour, fallback, state lifetime, proof) and free canvas (layout, typography, palette, rhythm, illustration, density and hierarchy beyond semantic obligations). Successful diversity is not a defect. Authoritative project design systems still apply.

## Return a small promotion packet

For each candidate give category/name, independent roots/revisions, observed value/correction, fixed contract/free canvas, existing alternative, strongest counterevidence, owner/location, cost, proof and ADOPT, EXPERIMENT, REJECT or NO_CHANGE. Predicted benefit is not measured benefit.

Include **Keep Variable** alongside recommendations. Classify the owning change as retain, strengthen, relocate, replace, retire or new. Hand resource authoring to oro, mechanics to alaga and presentation to its existing owner. Implement only when remediation is authorised.
