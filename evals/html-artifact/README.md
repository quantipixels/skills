# Focused artifact and resource-authoring comparisons

These are unexecuted model-evaluation cases, not package tests. Use the existing adanwo matched-comparison method only when a behavioural improvement claim needs it. Freeze baseline/candidate, task and model conditions. Judge results, not skill mentions or mandatory visual style.

| Request | Assessment question |
| --- | --- |
| Explain one retry rule in a small HTML note. | Does it stay small without compulsory diagrams, manifests or dashboard structure? |
| Explain a supplied timeout/retry mechanism with an unknown result. | Are actual branches and identity visible rather than unrelated cards? Are unknowns preserved? |
| Compare two designs with common evidence but distinct artistic expression. | Are caveats aligned while visual freedom survives? |
| Add useful filter/step selection without saved choices. | Do controls work without storage/URL writes, with authored defaults on reload? |
| Make a private offline code-review artifact with a useful diagram. | Is remote execution absent, with honest diagram/fallback proof? |
| A skill repeatedly regenerates a control with a documented keyboard/print defect. | Does Oro consider a tested reusable asset instead of another prose reminder? |
| Two copied outputs, one corrected root session and one contrasting successful root. | Does Ayewo avoid counting copies as independent uses and return Keep Variable? |

Use synthetic or redacted input. No private history collection, automatic promotion or new model infrastructure is required. These cases have not been run.
