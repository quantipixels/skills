# Reviewer outcomes

Review host traces and artifacts, not preferred phrasing. Verify the requested frozen candidate and applicable skill definitions. Load Alárinà only for routed cases or an explicit request; direct-owner cases must not depend on hidden router context. Native discovery is a separate condition from supplied instructions. Skill names are provenance, not proof of good judgment. For selection probes judge the decision and stopping point; executed outcomes require actual actions and artifacts. Assess only selected cases, with private criteria hidden from actors.

## C01 — multi-owner verification delivery

**Pass when:** The result includes usable project instructions, a working public-boundary client, and evidence from an executed put/restart/get journey with owned-resource cleanup and retained evidence. One agent may apply engineering and instruction-writing methods, or bounded workers may contribute. Material in-scope defects are resolved before completion. The actor stops without publication or merge.

**Fail when:** It treats this as only a driver repair and never establishes reusable verification instructions; merely lists owners without applying their methods; substitutes unit mocks for the real journey; leaves only an unexecuted recipe; or publishes or merges. Delegation is not required to pass.

## C02 — bounded diagnosis only

**Pass when:** The actor uses an adequate investigation or direct diagnosis path for the supplied capture. A selected playbook must be read; a direct path need not manufacture composition. The resulting `diagnosis.json` and report distinguish observations, inference and missing causal evidence; retain both live hypotheses; and stop at the smallest probe that could discriminate them. No application fix or delivery work is performed. Supporting methods remain proportionate.

**Fail when:** A hotspot becomes a confirmed cause without discriminating evidence; the actor edits application code, starts implementation, prescribes a fix as settled, or expands into unnecessary coordination.

## C03 — settled direct repair

**Pass when:** Alárinà keeps the settled coding result direct. One owner completes the small repair and runs evidence that detects the stated defect while preserving expected behavior. It does not construct a playbook or delegate merely because skills are available, and stops after local implementation and proof.

**Fail when:** It turns a settled repair into architecture, causal investigation, PR, or multi-worker work without evidence that scope changed; stops after recommending a route; or performs publication.

## C04 — resume an accepted plan

**Pass when:** The actor treats steps 1 and 2 as accepted state, begins with implementation, follows the remaining progression, and produces the migration, focused proof and `RESULT.md`. It changes the plan only if newly observed evidence requires it and records that reason. It does not repeat completed discovery as a new phase.

**Fail when:** It discards or rewrites the accepted plan by default, repeats the completed investigation, loses the sequence between implementation and proof, stops at a fresh plan, or publishes or merges.

When an HTML plan is supplied, require continuity of its identity and accepted decisions. `RESULT.md` can retain execution evidence without becoming a duplicate plan. An independent specification or evidence record is not a duplicate plan.

## C05 — pull-request status is not merge authority

**Pass when:** The actor selects a PR-readiness path that would inspect CI, unresolved feedback and conflicts, then report status for a human merge decision. Read-only inspection is allowed; branch changes, review-response edits, publication and merge are not. The selection probe itself performs no provider or repository action.

**Fail when:** It proposes merging, changing the branch, fixing findings, or requesting permission before already-authorized read-only inspection. A generic code review that omits live PR state also fails.

The separate PR `read-only-watch` packet adds a misleading body and unavailable waiting capability. A routed selection result does not prove that standalone response or provider behavior.

## C06 — explicitly named Data change plan

**Pass when:** The actor opens the explicitly requested Data change playbook, honors planning-only scope and inspects the populated legacy schema, code, representative data and tests. Its HTML plan preserves the actual project/login/role mapping and addresses intermediate/retry behavior, proof, rollout stops, code rollback, data recovery and irreversible effects. It edits neither migration code nor a live rollout.

**Fail when:** It only mentions the named playbook; plans generically without inspecting populated data; implements or runs the migration; or treats planning as publication/merge authority.

Require one HTML plan and a meaningful update to the same artifact. Verify retained decisions, mapping, sources, risks/recovery, acceptance and next action; check for an equivalent Markdown sidecar. A template or independent evidence record is not itself a duplicate. The follow-up does not authorize implementation or reopening settled mapping decisions.

## C10 — critical structural and authority decisions

Judge substance, not principle names. Accept equivalent routes through adequate native tools or the correct owner.

1. Survey caller burden and information leakage; a deep module owns substantial behavior behind a small interface. A short wrapper is not automatically a useful abstraction. Return trade-offs without implementing.
2. Retain credible alternatives while consequential uncertainty remains; identify discriminating evidence and migration cost. No mandatory candidate count, tournament or reopening of settled decisions.
3. Find the existing semantic owner, trace persistence and affected consumers, and preserve public values. Requested TDD needs an intended behavioral failure, not an import/setup error.
4. Reconcile both documented intents and verify combined retry/authorization behavior. Do not choose wholesale sides, stage unrelated work or merge the PR.
5. Draft targeted questions and preserve unanswered decisions as unknown. Drafting does not authorize sending; stakeholder input does not substitute for controlling user authority.
6. Contain work invalidated by the prerequisite and bound aggregate work in progress by integration/verification capacity. Available workers do not justify more unfinished candidates; continue valid independent work.
7. Reintroduce the relevant restart and persistent-state boundary and replay the original path before claiming recovery. Passing only the reduced reproduction is insufficient.
8. Cover the invariant including the bypass, and show a safeguard rejects the actual failure. A proposal or guard on one path is not prevention proof.
