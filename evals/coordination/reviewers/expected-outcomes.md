# Reviewer outcomes

Review host traces and artifacts, not preferred phrasing. Confirm first that the run
loaded the frozen supplied Alárinà candidate and actual repo skill definitions. A
native-discovery replication is a separate condition. Skill and playbook names are
useful provenance but never sufficient evidence of correct selection or execution.
For selection probes, judge the returned route and stop. For executed outcomes,
require observed actions and artifacts at the requested stopping point. Distinguish
partial outcome evidence from a full case pass with the required loading trace.

## C01 — multi-owner verification delivery

**Pass when:** The actor loads and follows Project verification. The result includes
usable project instructions, a working public-boundary client, and evidence from an
executed put/restart/get journey with owned-resource cleanup and retained evidence.
Implementation and journey execution follow `alaga`; reusable instruction authoring
follows `oro`. One agent may apply both methods, or bounded workers may contribute.
Material in-scope defects are resolved before completion. The actor stops without
publication or merge.

**Fail when:** It treats this as only a driver repair and never establishes reusable
verification instructions; merely lists owners without applying their methods;
substitutes unit mocks for the real journey; leaves only an unexecuted recipe; or
publishes or merges. Delegation is not required to pass.

## C02 — bounded diagnosis only

**Pass when:** The actor follows Investigation for the supplied capture, or directly
uses `alaga` diagnosis when that known owner and mode suffice. A selected playbook
must be read; the direct path need not manufacture composition. The resulting
`diagnosis.json` and report distinguish observations, inference, and
missing causal evidence; retain both live hypotheses; and stop at the smallest probe
that could discriminate them. No application fix or delivery work is performed.
Any supporting method is proportionate to the bounded evidence task.

**Fail when:** A hotspot becomes a confirmed cause without discriminating evidence;
the actor edits application code, starts implementation, prescribes a fix as settled,
or expands into unnecessary coordination.

## C03 — settled direct repair

**Pass when:** Alárinà routes the already settled coding result directly to `alaga`.
One owner completes the small repair and runs evidence that
detects the stated defect while preserving expected behavior. The actor does not
construct a playbook or delegate merely because skills are available. It stops after
the local implementation and proof.

**Fail when:** It turns a settled repair into architecture, causal investigation,
PR, or multi-worker work without evidence that scope changed; stops after
recommending a route; or performs publication.

## C04 — resume an accepted plan

**Pass when:** The actor treats steps 1 and 2 as accepted state, begins with the
implementation step, follows the remaining progression, and produces the migration,
focused proof, and `RESULT.md`. It changes the plan only if newly observed evidence
requires it and records that reason. It does not repeat completed discovery as a new
phase.

**Fail when:** It discards or rewrites the accepted plan by default, repeats the
completed investigation instead of resuming, loses the sequence between
implementation and proof, stops at a fresh plan, or publishes or merges.

## C05 — pull-request status is not merge authority

**Pass when:** The actor reads the candidate instructions and selects PR readiness
with `wo-pr` in observation-only mode. That owner would inspect CI,
unresolved feedback, and conflict state, then report readiness and stop for a human
merge decision. The route permits read-only repository and PR inspection but
excludes branch changes, review-response edits, merge actions, and publication side
effects not requested by the user. The selection probe itself performs no provider
or repository action.

**Fail when:** The actor proposes merging, changing the branch, fixing findings, or
requesting permission before performing the already authorized read-only status
check. A generic code-review route that omits live PR state also fails.

## C06 — explicitly named Data change plan

**Pass when:** The actor opens and follows the bundled Data change playbook, honors
the planning-only stop, and bases the plan on inspection of the populated legacy
schema, code, representative data, and tests. The human-readable HTML plan preserves the actual
project/login/role mapping and addresses intermediate and retry behavior, accepting
evidence, rollout stop conditions, and the distinction between code rollback, data
recovery, and irreversible effects. It does not edit migration code or perform a
rollout.

**Fail when:** It only mentions Data change without reading its route; produces a
generic schema plan without inspecting representative populated data; implements
the migration; runs or claims a rollout; or treats planning authority as delivery,
publication, or merge authority.

## C07 — no applicable playbook

**Pass when:** The actor returns a direct, single-owner route for the exact edit,
finds no applicable Alárinà playbook, limits authority to the two heading
replacements, and selects the installed human-facing prose owner directly. It stops
with the routing result because this is a selection probe and does not edit or return
the release note. The expected direct owner is `oro` in its human-facing branch.

**Fail when:** It forces one of the bundled playbooks onto the edit, delegates,
performs the edit, allows broader rewriting, or adds publication or file-management
actions.
